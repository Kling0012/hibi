## 現在のメタデータと送信量

ウィンドウのフレームには取得したソース自身の名前を付けます。前面ウィンドウの ID が一致するときだけ、その app・title・url を使います。画面のフレームには、前面ウィンドウがその画面の範囲内に収まるときだけ app・title・url を付けます。ウィンドウが複数画面にまたがる場合や所属を確認できない場合は空にします。

`capture.live_fps` は選択対象ごとの頻度です。1回の tick で選択数ぶん送るため、合計送信量の上限は `live_fps × 選択数` 枚/秒です。対象がない場合や取得に失敗した場合、処理中の tick は送信されないため、実際の送信量は減ることがあります。

## 実行方法

リポジトリ直下で実行します。

```sh
pnpm --dir frontend install --offline --frozen-lockfile --ignore-scripts
node --test frontend/scripts/reproduce-live-capture.cjs
```

環境は Linux、Node.js v22.23.2、pnpm 10.34.6、TypeScript 6.0.3、dayjs 1.11.23 です。依存関係は worktree 外の既存の pnpm キャッシュから準備しました。

スクリプトは実際の `screen-monitor-task.ts` と `LiveCaptureService.ts` を TypeScript で変換して読み込みます。UI が呼ぶ IPC ハンドラーに設定・選択対象・開始を順に渡し、Live サービスが登録したタイマーを実行します。内部の判定メソッドや tick を直接呼ぶ方式ではありません。

時刻、Electron、画面ソース、ウィンドウ情報、HTTP 通信をモックしています。時間判定には実際の dayjs とプラグインを使います。画面ソースは第1ディスプレイ、第2ディスプレイ、ウィンドウ一つを用意し、JPEG の代わりに対象 ID を含む合成データを返します。送信先と送信データはメモリ内に記録します。実際の画面取得や通信は行いません。

## コード上で確認した経路

- `frontend/src/main/background/task/screen-monitor-task.ts:38` の選択対象 IPC はログを出力しますが、Live サービスへ対象を渡しません。
- 同ファイルの44行目では時間設定を `modelConfig` に保存します。84行目の `startTask` は `checkCanRecord` を呼ばず、Live を開始します。
- 同ファイルの57行目の IPC は録画可否を返しますが、Live の停止や設定更新は行いません。
- `frontend/src/main/services/LiveCaptureService.ts:102` は screen ソースを取得し、108行目で最初の有効な display ID を持つソースを選びます。選択したウィンドウや第2ディスプレイは参照しません。
- 同ファイルの97・106・117行目では実行中・離席・処理中を確認しますが、録画時間・曜日を確認せず、123行目の送信へ進みます。
- `frontend/src/renderer/src/pages/screen-monitor/screen-monitor.tsx:406` の時間設定保存処理は画面側の値を更新します。`updateModelConfig` を呼ぶのは194行目の開始処理だけです。モック再現では IPC まで新設定を届けても Live に反映されないことを確認しました。画面の保存操作から IPC への反映は別途修正対象です。

## 判断したこと

許可時間の終了を含めないという依頼仕様に従って、終了時刻ちょうどのケースでは録画不可を期待値にしました。既存の `checkCanRecord` は `isBetween(..., '[]')` と `isSameOrBefore` を使い、終了時刻を含んでいます。仕様の前提にある「既存の挙動に合わせる」とは食い違うため、修正担当へこの事実を引き継ぎます。
